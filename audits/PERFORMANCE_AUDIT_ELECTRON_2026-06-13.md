## Executive Summary

The engine and data layers are, on the whole, **competently built for this scale** (~4,800 vouchers/year, ~559 items, ~472 ledgers): most heavy aggregations are single-pass O(V×L) scans into Maps, a voucher index and precomputed caches avoid per-render rescans, and several hot paths are already deferred to `requestIdleCallback`. There is **no engine-level OOM risk and no algorithmic catastrophe** in the five dimensions audited.

The real performance cost is concentrated in a handful of places, and they share one root cause: **large synchronous work on the single thread that the Electron main process and the React renderer both depend on.** Specifically:

1. **The Express proxy runs *inside* the Electron main process** (`require(serverDist)`), so the ~50 MB Tally XML→JSON conversion competes with window/IPC responsiveness on the same event loop. This is the highest-leverage structural issue found.
2. **Data hydration and IndexedDB persistence do full synchronous `JSON.parse` / Map↔array (de)serialization of the 100–500 MB object graph on the renderer UI thread**, causing multi-hundred-ms (potentially multi-second) freezes on boot and on every persist.
3. **The co-purchase / upsell analysis in `generatePredictions` is genuinely O(P·I²)** — the single most expensive user-triggered computation, and it runs twice per import.
4. **Background sync timers stack** (5-min-after-Tally + 15-min interval + 30-min Tally + hourly DN) and can push the full multi-hundred-MB payload to Supabase repeatedly with no debounce/coalescing.

After verification, the confirmed counts are below. (Note: the most severe *structural* issues — in-process server, sync persistence — were rated `high`; nothing reached `critical` because none reliably crashes or OOMs, but several `high`/`medium` items cause visible jank.)

## ⚡ Quick Wins (high impact ÷ low effort — do these first)

- **`ELEC-01` — Window creation is serialized behind full server boot — blank screen during cold start** (🟠 HIGH, S): Reorder the whenReady callback so the window is created first and the server starts in parallel. Move `createWindow()` to be the first statement, then call `startExpressServer()` without awaiting it, keeping the existing try/catch as a `.catch()` that shows the error dialog: `app.whenReady().then(() => { createWindow(); startExpressServer().then(() => console.log('Server ready on :3100')).catch(err => { console.error('Server failed:', err.message); dialog.showErrorBox('API Server Error', ...); }); register shortcuts; });`. This removes the entire server-boot time (require() eval + isPortFree + waitForServer priming/retries, and crucially the stale-port 800ms+20s worst case) from time-to-first-paint. The renderer already tolerates an absent server (isConnected defaults false, auto-sync is on a 10s+30min timer, data restores from IndexedDB), so no UI breaks. Optionally broadcast a `mainWindow.webContents.send('server-ready')` after waitForServer resolves so any view that wants to enable Tally features can react, rather than the renderer polling. Low-risk, S-effort, single-file change.
- **`ENG-03` — ItemsAnalytics mount fires two independent full voucher scans (turnover + margins)** (🟡 MEDIUM, S): Read itemMargins from the store (useDataStore selector) instead of calling computeItemMargins in the component. If turnover must stay client-side, either also precompute it in dataStore alongside margins, or merge the turnover and margin accumulation into one shared single-pass helper that returns both per-item structures.
- **`PROXY-05` — console.log is monkey-patched to push every log line into an in-memory buffer, and the converters log per-sync hot data** (🟡 MEDIUM, S): Gate the verbose per-dataset logs (convert.ts:166-173 and 322-334) behind a DEBUG env flag so they don't run during normal syncs. Make the console override cheap: skip args.join unless the buffer actually has SSE/HTML consumers, and use a ring-buffer index instead of Array.shift() (shift is O(n) on a 500-element array every call past the cap).
- **`PROXY-06` — 100mb express.json body limit + synchronous parse of inbound config-sync payloads on the UI thread** (🟡 MEDIUM, S): Primary fix is utilityProcess isolation (PROXY-01). Independently, lower the limit to the realistic maximum and, for the big config/voucher pushes, stream-ingest (e.g. line-delimited) rather than buffering+parsing one giant JSON object. Confirm the renderer isn't round-tripping data through HTTP that it could write to Supabase/IndexedDB directly.
- **`BG-03` — Full Supabase push fires regardless of whether any data changed (no dirty check)** (🟡 MEDIUM, S): Gate the masters+vouchers push on data.importedAt (already a change sentinel — usePersistenceMonitor uses it the same way at usePersistenceMonitor.ts:39). Store lastPushedImportedAt; skip pushAll if data.importedAt === lastPushedImportedAt. The hourly DN refresh should only bump lastSync when dnCount > 0 or the DN set actually changed.
- **`BG-04` — Config sync pushes to Supabase ~2s after every cold boot even with zero user edits** (🟡 MEDIUM, S): Add a hasMountedRef (skip the very first effect run), or compare a stable hash of the payload against the last-pushed hash and bail if unchanged. Optionally wait until zustand persist hydration completes before arming the first debounce.
- **`DATA-05` — Manual sync handlers double-serialize and double-write the dataset (persistence monitor + explicit saveData)** (🟡 MEDIUM, S): Pick one owner of the parsedData write. Since usePersistenceMonitor already saves on every data change, remove the explicit `saveData('parsedData', serializeParsedData(...))` calls from the sync handlers (keep them only where a synchronous write before navigation is genuinely required, and in that case skip the monitor's redundant write by advancing lastSavedRef). This halves serialization+write cost per sync at zero behavioral loss.
- **`DATA-06` — 5-minute auto-backup serializes the entire dataset again into the backups store, multiplying IDB storage and write cost** (🟡 MEDIUM, S): Guard the backup with the same importedAt sentinel so it only snapshots when data actually changed since the last backup, and skip it entirely if a backup already exists for the current importedAt. Reduce keepBackups (e.g. 3) and/or store backups as deltas. Move the serialize into the worker. Consider lengthening the interval to 30-60 min given how heavy each snapshot is.
- **`DATA-07` — Raw uploaded JSON (23-25MB each) retained in IndexedDB alongside the parsed canonical form — duplicate memory/storage** (🟡 MEDIUM, S): Either stop persisting the raw upload once canonicalization succeeds (the canonical form is the source of truth and is itself backed up), or store only a compressed/gzipped copy if re-import is genuinely needed. At minimum drop keepJsonUploads to 1-2 and null out the in-memory raw reference (`mastersRaw = null; txRaw = null`) immediately after parseMasters/parseTransactions return so the GC can reclaim it before the heavy index build.
- **`ELEC-05` — Continuous requestAnimationFrame FPS loop runs from boot and never lets the renderer idle** (🟡 MEDIUM, S): Stop re-scheduling the rAF when not recording: inside tick, only call requestAnimationFrame(tick) if store.getState().recording is true, and re-arm the loop from startRecording(). Alternatively default `recording: false` and let the user enable perf capture from the PerfLog page only when diagnosing. This lets the renderer genuinely idle when the app is sitting on a static view.

## Detailed Findings by Dimension

### Electron Main Process & Boot Path

> **Assessment:** The boot path is correctly hardened in several ways: single-instance lock guards against double-launch (electron.js:23-26), the renderer V8 cap is sensibly chosen for the 100-500MB data scale (electron.js:18), `v8CacheOptions:'code'` and `spellcheck:false` are good defaults, IDB restore is wrapped in startTransition to keep the UI interactive (App.tsx:112), and `backgroundColor:'#ffffff'` + `show:false`/`ready-to-show` avoids a white flash. However the cold-start path is needlessly serialized: the BrowserWindow is created only AFTER `await startExpressServer()` fully resolves (electron.js:245 then :252), so the user stares at nothing while the in-process `require()` of a 50MB-dependency Express/Supabase bundle runs on the main thread and a port-probe + 300ms-primed poll loop completes. The Express server is loaded into the main process via `require()`, so its module-eval and every subsequent request handler compete with the same thread that drives window creation and IPC. GPU is fully disabled (`disable-gpu` + `disable-software-rasterizer`), which forces the Leaflet map and any future canvas onto a pure-CPU paint path. Several IPC handlers re-read and JSON.parse config files from disk synchronously on every call. A perpetual requestAnimationFrame FPS loop runs from boot and never lets the renderer idle. The findings below are ordered by boot-latency and steady-state impact.

#### `ELEC-01` — Window creation is serialized behind full server boot — blank screen during cold start

- **Severity:** 🟠 HIGH  ·  **Effort:** S  ·  **Confidence:** 0.95
- **Category:** boot-latency
- **Locations:** `public/electron.js:242-252`, `public/electron.js:93-138`
- **Evidence:** app.whenReady().then(async () => { ... await startExpressServer(); console.log('Server ready on :3100'); ... createWindow(); }). createWindow() (line 252) only runs AFTER startExpressServer() resolves. startExpressServer itself awaits isPortFree(3100), then require(serverDist) (synchronous module eval of the Express/Supabase bundle), then `return waitForServer(3100, 20000)` which only begins probing after `setTimeout(check, 300)` and retries every 250ms (electron.js:58,61).
- **Impact:** The OS window does not appear until the Express server is listening AND has answered an HTTP probe. Best case adds the require() eval time + 300ms poll priming + one ~250ms retry cycle (~0.6-1s of pure blank) before the window even starts loading the renderer; worst case (stale port, see ELEC-02) adds seconds. The renderer (which can run fully offline against IndexedDB) is needlessly gated on a backend it doesn't need to paint the first frame.
- **Root cause:** Boot treats the API server as a hard prerequisite for the UI, but the renderer restores from IndexedDB and only needs the server for Tally/Supabase sync — work that happens minutes later on timers.
- **Recommendation:** Create the window FIRST and start the server in parallel: call createWindow() immediately in whenReady, and kick off startExpressServer() without awaiting it (fire-and-forget with the existing try/catch error dialog). The renderer already tolerates an absent server (electronAPI checks, sync hooks are on timers). Optionally broadcast a 'server-ready' IPC event so any UI that needs the API can react. This removes the entire server-boot time from time-to-first-paint.
- **🔍 Verification:** Confirmed by reading the cited code. electron.js:242-252: `app.whenReady().then(async () => { try { await startExpressServer(); ... } catch {...} createWindow(); })` — createWindow() (252) runs strictly after the awaited startExpressServer() settles, so the OS window is gated on the full server boot. startExpressServer() (93-138) awaits isPortFree(3100), synchronously evaluates `require(serverDist)` (134) which loads the entire Express+Supabase+Tally+dotenv bundle into the main process, then returns waitForServer(3100,20000) (137). waitForServer (45-63) does `setTimeout(check,300)` before the first probe (61) and retries every 250ms on error (58), so the happy path has a ~300ms priming floor plus require() eval time plus a likely first-retry cycle before resolve. The supporting premise — that the renderer needs none of this to paint — is also confirmed: tallyStore.isConnected defaults to false (tallyStore.ts:40) so useTallyAutoSync.runSync early-returns (useTallyAutoSync.ts:39) and is further gated behind a 10s setTimeout (91); App.tsx restores state from IndexedDB on boot (109-115); the dev renderer loads from Vite :5173 not Express (electron.js:167); preload's electronAPI talks to the main process via IPC, not the Express server. So nothing the renderer does for first paint depends on :3100. The window is needlessly serialized behind a backend it doesn't need to render. Note the `show:false` + `ready-to-show` pattern (163,171) means the user sees no window at all (not even a blank frame) until after the server resolves AND the renderer is ready — making the perceived blank period the sum of server-boot + renderer-load rather than overlapping them. The only nuance vs. the finding: createWindow() IS reached even on server failure (it's after the catch), so it's not a permanent hang on the happy/error path — but on the ELEC-02 stale-port path the catch only settles after the 800ms sleep + 20s waitForServer timeout, so the window is delayed by seconds on every crash-recovery boot.
- **How to measure:** Add high-resolution timestamps in electron.js: capture t0 at the top of the whenReady callback, log `performance.now()` immediately before `require(serverDist)` and immediately after it returns (isolates pure module-eval cost), log again when waitForServer resolves, and log inside createWindow() and in the `ready-to-show` handler. The delta from t0 to ready-to-show is the true time-to-first-paint. Run three scenarios: (a) clean boot (port free) to measure require()-eval + ~300ms priming + first-probe latency; (b) warm boot with the v8 code cache populated; (c) stale-port boot (leave a dangling node on 3100, or a non-responsive listener) to measure the 800ms sleep + up-to-20s waitForServer worst case. Then apply the fix (createWindow() first, fire-and-forget server) and re-measure ready-to-show — the server-boot delta should drop out of TTFP entirely. Cross-check require() cost independently with `node --eval "const t=performance.now(); require('./server/dist/index.js'); console.log(performance.now()-t)"` against the built server bundle.
- **Refined recommendation:** Reorder the whenReady callback so the window is created first and the server starts in parallel. Move `createWindow()` to be the first statement, then call `startExpressServer()` without awaiting it, keeping the existing try/catch as a `.catch()` that shows the error dialog: `app.whenReady().then(() => { createWindow(); startExpressServer().then(() => console.log('Server ready on :3100')).catch(err => { console.error('Server failed:', err.message); dialog.showErrorBox('API Server Error', ...); }); register shortcuts; });`. This removes the entire server-boot time (require() eval + isPortFree + waitForServer priming/retries, and crucially the stale-port 800ms+20s worst case) from time-to-first-paint. The renderer already tolerates an absent server (isConnected defaults false, auto-sync is on a 10s+30min timer, data restores from IndexedDB), so no UI breaks. Optionally broadcast a `mainWindow.webContents.send('server-ready')` after waitForServer resolves so any view that wants to enable Tally features can react, rather than the renderer polling. Low-risk, S-effort, single-file change.

#### `ELEC-03` — Express + Supabase + fast-xml-parser bundle is require()'d into the Electron main process, sharing its thread

- **Severity:** 🟠 HIGH  ·  **Effort:** L  ·  **Confidence:** 0.85
- **Category:** main-thread-contention
- **Locations:** `public/electron.js:133-137`, `server/dist/index.js:6-24`, `server/dist/services/syncOrchestrator.js:9,13`
- **Evidence:** electron.js:134 `require(serverDist)` loads the CJS server bundle directly into the main process (no child process). The server module eval is heavy and synchronous: server/dist/index.js requires express, cors, @supabase/supabase-js (7.5MB package on disk), ws, fast-xml-parser, and constructs top-level singletons `new ChangeDetector()` and `new SyncOrchestrator(...)` (index.js:17-18). SyncOrchestrator's field initializer `supabase = new SupabaseSync()` (syncOrchestrator.js:13) runs at construction, which executes the supabase require chain. app.listen is only reached at server/dist/index.js:524 — the entire route table builds synchronously first.
- **Impact:** Two costs: (1) Module eval of the full express/supabase/xml dependency tree runs synchronously on the main thread at boot, lengthening the window-creation delay (ELEC-01/02). (2) For the app's lifetime, every Express request handler — including the heavy `convertCompanies`/XML parsing of ~50MB Tally exports (convert.js, 391 lines) — executes on the SAME thread that handles IPC, dialog, and window events. A long XML parse or a big Supabase batch push will jank the main process and stall IPC round-trips (get-settings, discount-rules) and window responsiveness.
- **Root cause:** Co-locating the API server in the main process was chosen to avoid Windows spawn issues, but it couples backend CPU work to Electron's UI/IPC event loop with no isolation.
- **Recommendation:** Move the server into a utilityProcess (Electron 22+ `utilityProcess.fork`) or a hidden child_process — it gives a separate V8 isolate/thread so XML parsing and Supabase work can't block IPC or window events, while keeping a single bundled node runtime (no external spawn of system node). If staying in-process is required, at minimum offload the CPU-heavy XML conversion (convert.js) to a worker_thread so request handling doesn't stall the UI thread. Defer the supabase require until first sync (lazy-instantiate SupabaseSync) so boot module-eval is lighter.

#### `ELEC-05` — Continuous requestAnimationFrame FPS loop runs from boot and never lets the renderer idle

- **Severity:** 🟡 MEDIUM  ·  **Effort:** S  ·  **Confidence:** 0.85
- **Category:** steady-state-cpu
- **Locations:** `src/hooks/usePerfMonitor.ts:126-146`, `src/store/perfStore.ts:103`, `src/App.tsx:68`
- **Evidence:** usePerfMonitor (mounted at App root, App.tsx:68) runs `function tick(){ fpsFrames.current++; ... rafHandle.current = requestAnimationFrame(tick); }` and re-schedules unconditionally every frame (usePerfMonitor.ts:141-143). Only the SAMPLE push is gated on `store.getState().recording`; the rAF itself always re-arms. perfStore defaults `recording: true` (perfStore.ts:103), so it is active by default with no user opt-in.
- **Impact:** A self-perpetuating rAF callback fires ~60x/sec for the entire app lifetime, keeping the renderer's main thread continuously scheduled and preventing the compositor from going idle. On a desktop business app left open all day this is a constant low-grade CPU/battery cost and works against any power-saving idle behavior. It runs even on static pages where no animation is occurring.
- **Root cause:** FPS instrumentation re-schedules the rAF independent of whether recording is enabled, and recording defaults to on.
- **Recommendation:** Stop re-scheduling the rAF when not recording: inside tick, only call requestAnimationFrame(tick) if store.getState().recording is true, and re-arm the loop from startRecording(). Alternatively default `recording: false` and let the user enable perf capture from the PerfLog page only when diagnosing. This lets the renderer genuinely idle when the app is sitting on a static view.

#### `ELEC-02` — Stale-port recovery path runs synchronous netstat + taskkill + 800ms sleep on the main thread before window opens

- **Severity:** 🟡 MEDIUM  ·  **Effort:** M  ·  **Confidence:** 0.9
- **Category:** boot-latency
- **Locations:** `public/electron.js:109-131`, `public/electron.js:76-88`
- **Evidence:** if (!portFree) { ... await waitForServer(3100, 3000); ... } catch { killPortProcess(3100); await new Promise(r => setTimeout(r, 800)); ... }. killPortProcess runs execSync('netstat -ano', {timeout:3000}) (line 78) — a fully blocking child process spawn that parses the ENTIRE system socket table, then execFileSync('taskkill', ...) per matching PID (line 84). All of this is inside the awaited startExpressServer, which (per ELEC-01) blocks createWindow.
- **Impact:** When a previous instance left a dangling node listener (crash/forced-quit — exactly the scenario this code exists for), cold start pays: up to 3s waitForServer probe + a blocking netstat scan (can take 100s of ms on a busy Windows box) + taskkill + a hard 800ms sleep + a second isPortFree check. That is multiple seconds of blank window on precisely the unhappy path users hit after a crash.
- **Root cause:** execSync/execFileSync are synchronous and block the main process event loop; combined with ELEC-01 they block window creation entirely. netstat -ano with no port filter dumps every connection.
- **Recommendation:** First, adopt ELEC-01 so this path never blocks the window. Second, make the kill async: use child_process.exec (callback/promise) instead of execSync/execFileSync. Third, scope the scan with `netstat -ano -p tcp | findstr :3100` (or use `Get-NetTCPConnection -LocalPort 3100`) so you don't parse the whole table. Replace the fixed 800ms sleep with a poll on isPortFree (e.g. retry every 100ms up to 800ms) so a fast OS release returns immediately.

#### `ELEC-04` — GPU fully disabled (disable-gpu + disable-software-rasterizer) forces Leaflet map and all canvas paint onto the CPU

- **Severity:** 🟡 MEDIUM  ·  **Effort:** M  ·  **Confidence:** 0.7
- **Category:** rendering-perf
- **Locations:** `public/electron.js:10-12`, `src/pages/Routes.tsx:2,221`

### Data Ingestion, Parsing & Memory

> **Assessment:** The ingestion pipeline is functionally correct and shows real prior optimization effort (voucherIndex/stockMap/partyStats/ledgerTxnMap pre-computed, idle-callback deferral of heavy derived work, a 500ms persist debounce keyed on an O(1) `importedAt` sentinel, iterate-and-set merges instead of double-spread). However, every stage of the data path runs synchronously on the main renderer thread with zero Web Worker offload: 23-25MB raw files are parsed with a single blocking `JSON.parse`, the ~100-500MB parsed object graph is re-serialized to a JSON string and written to IndexedDB in full on every voucher change (no diffing/incremental write), and `voucherIndex`+`stockMap` are rebuilt from scratch on every `setData`. On top of this, two independent Supabase auto-push hooks (15-min interval + 5-min-after-Tally) each `Array.from` the Maps and `JSON.stringify` the entire voucher array with full inventory lines on the main thread, the manual sync handlers double-write (persistence monitor + an explicit `saveData`), a 5-min auto-backup serializes the whole dataset yet again, and the raw uploaded JSON is retained in IDB alongside the parsed form. For the current ~4,800-voucher/yr scale the parse and single-write costs are seconds-of-jank, not OOM; the write amplification and redundant full-dataset serializations are the more chronic, compounding cost and will scale poorly as multi-year history accumulates.

#### `DATA-05` — Manual sync handlers double-serialize and double-write the dataset (persistence monitor + explicit saveData)

- **Severity:** 🟡 MEDIUM  ·  **Effort:** S  ·  **Confidence:** 0.85
- **Category:** persistence
- **Locations:** `src/pages/Import.tsx:183-184`, `src/pages/Import.tsx:259-262`, `src/pages/Import.tsx:798-800`, `src/hooks/useTallyAutoSync.ts:60-71`, `src/hooks/usePersistenceMonitor.ts:43-65`
- **Evidence:** Every sync path does `startTransition(() => mergeData(data));` (which sets fresh state → flips data.importedAt → triggers usePersistenceMonitor to serialize+write the whole blob) AND immediately `await saveData('parsedData', serializeParsedData(merged))` / `serializeParsedData(data)` on the same data. useTallyAutoSync does the identical pair: `mergeData({...}); ... await saveData('parsedData', serializeParsedData(merged))`. So serializeParsedData (full Array.from of Maps) runs twice and the structured-clone IDB write happens twice for one logical sync.
- **Impact:** Doubles the most expensive persistence operation per sync — two full Array.from(Map.entries()) conversions and two structured-clone writes of the entire dataset. The two writes also race on the same key, and the explicit one isn't debounced, so it lands during the same frame as the merge while the monitor's debounced write fires 500ms later writing the same bytes again.
- **Root cause:** Redundant belt-and-suspenders persistence: the explicit saveData predates (or distrusts) the usePersistenceMonitor effect, and neither was removed when the other was added.
- **Recommendation:** Pick one owner of the parsedData write. Since usePersistenceMonitor already saves on every data change, remove the explicit `saveData('parsedData', serializeParsedData(...))` calls from the sync handlers (keep them only where a synchronous write before navigation is genuinely required, and in that case skip the monitor's redundant write by advancing lastSavedRef). This halves serialization+write cost per sync at zero behavioral loss.

#### `DATA-06` — 5-minute auto-backup serializes the entire dataset again into the backups store, multiplying IDB storage and write cost

- **Severity:** 🟡 MEDIUM  ·  **Effort:** S  ·  **Confidence:** 0.85
- **Category:** persistence
- **Locations:** `src/hooks/usePersistenceMonitor.ts:74-103`, `src/db/idb.ts:79-85`
- **Evidence:** A second effect runs `setInterval(scheduledBackup, autoBackupInterval)` (default 5 min) and calls `createBackup(serializeParsedData(data), ...)`, which does `db.put('backups', { data, label, createdAt }, key)`. serializeParsedData again does the full Array.from of items/ledgers Maps and embeds the whole voucher array; each backup is a full copy of the dataset. pruneBackups keeps 10, so up to 10× the full dataset is retained in IDB.
- **Impact:** Every 5 minutes the full ~100-500MB-class dataset is re-serialized (main-thread Array.from + structured clone) and persisted as a fresh copy, even if nothing changed since the last backup. With keepBackups=10 this can hold roughly 10 full snapshots in IndexedDB, ballooning on-disk storage and adding a recurring serialization spike independent of actual edits.
- **Root cause:** Time-based full-snapshot backup with no change detection — it backs up on a wall-clock timer rather than 'on meaningful change', and stores complete copies rather than diffs.
- **Recommendation:** Guard the backup with the same importedAt sentinel so it only snapshots when data actually changed since the last backup, and skip it entirely if a backup already exists for the current importedAt. ### Background Work, Timers & Async Sync

> **Assessment:** The app mounts 8 always-on background hooks at the React root (App.tsx:61-83). Most are correctly written — they read mutable state through refs, debounce config writes, defer heavy work to requestIdleCallback, and clean up their timers on unmount. The real problems concentrate in the "push EVERYTHING to Supabase" path: two independent hooks (useSupabaseAutoPushAfterTally, useSupabaseAutoPushInterval) both serialize the ENTIRE parsed dataset (items + ledgers + ~4800 vouchers with full inventory/ledger lines) to JSON on the renderer main thread and POST it to the local proxy — on a 15-min interval, 5 min after every Tally sync, plus a 60s retry — with no in-flight guard, so they can stampede and re-stringify tens of MB repeatedly even when nothing changed. None of these freeze the UI catastrophically, but the repeated whole-dataset JSON.stringify on the main thread is a real multi-hundred-ms jank source at this data scale, and the redundant/overlapping pushes waste bandwidth and Supabase write quota. Timer cleanup itself is solid across all hooks.

### Express Proxy Server & XML Conversion

> **Assessment:** The Express proxy is architecturally sound in its network handling — node:http with socket-level timeouts and chunk-reset logic (tally.ts) is genuinely better than fetch() for Tally's bursty slow responses, AbortSignal listener cleanup is correct, concurrency is sensibly capped (3 voucher chunks), GUID dedup is O(1), and Supabase writes are batched and fire-and-forget. The fatal flaw is WHERE this code runs: electron.js:134 does `require(serverDist)`, loading the entire server into the Electron MAIN process. Every synchronous operation in this server — XML DOM parsing, the per-field regex conversion, and JSON.stringify of the final result — blocks the single event loop that ALSO handles IPC and serves the renderer's own fetch() calls to localhost:3100. At this data scale (50MB XML responses parsing into 100-500MB of JS objects), several of these synchronous steps are multi-second main-thread stalls that freeze the whole desktop app, and the worst-case full-FY sync layers them: parse → convert → buffer the entire result in memory → JSON.stringify → ship over HTTP, all on the one thread. The findings below are ordered by blocking severity; PROXY-01 (synchronous DOM XML parse) and PROXY-02 (JSON.stringify of the whole dataset) are the two worst offenders.

#### `PROXY-01` — Synchronous DOM-based XML parse of ~25-50MB Tally responses blocks the Electron main event loop

- **Category:** blocking-cpu
- **Locations:** `server/src/services/voucherPusher.ts:142-199`, `server/src/services/voucherPusher.ts:5`
- **Evidence:** voucherPusher.ts:146 first does `[...rawXml.matchAll(/<LINEERROR>([^<]*)<\/LINEERROR>/g)]`, then voucherPusher.ts:156 separately constructs a SECOND fast-xml-parser instance (voucherPusher.ts:5) and runs `parser.parse(rawXml)` over the same string, then on the fallback path (voucherPusher.ts:169-175) runs three more regex .match() scans over the full raw XML. Import responses are small, so this is not a freeze — but it's redundant double-work (regex scan + full DOM parse of the same document) on every voucher push.
- **Impact:** Negligible per call (import responses are tiny), but pushBatchToTally (voucherPusher.ts:214-238) calls pushVoucherToTally sequentially in a loop, so for a large batch push this redundant parse+regex runs once per voucher. Pure waste, not a UI risk.
- **Root cause:** Defensive multi-strategy parsing (regex first, DOM second, regex fallback) was written for robustness against Tally version quirks without consolidating the passes.
- **Recommendation:** Since import responses are small and structurally simple, drop the full XMLParser.parse and extract CREATED/ERRORS/LASTVCHID/LINEERROR with the regexes already present (the code already trusts regex as 'most reliable' for LINEERROR, voucherPusher.ts:145). This removes a second parser instance and an XML parse per push.

#### `PROXY-08` — killPortProcess uses execSync(netstat -ano) — synchronous child-process spawn blocking app boot

- **Severity:** ⚪ LOW  ·  **Effort:** S  ·  **Confidence:** 0.7
- **Category:** blocking-io
- **Locations:** `public/electron.js:76-88`, `public/electron.js:6`
- **Evidence:** electron.js:78 `const out = execSync('netstat -ano', { encoding: 'utf8', timeout: 3000, maxBuffer: 1024*1024 });` runs synchronously inside startExpressServer (electron.js:119), blocking the main process for the full duration of netstat (can be hundreds of ms on a busy machine) plus the synchronous string split/filter over potentially thousands of connection lines (electron.js:79). execFileSync('taskkill', ...) (electron.js:84) is also synchronous.
- **Impact:** Only triggers on the stale-port recovery path at startup, so it's not a steady-state issue, but it synchronously stalls app boot before the window is created (electron.js:242-252). netstat output on a machine with many sockets can be large and the synchronous line-filter scans all of it.
- **Root cause:** Startup port-recovery was implemented with the simplest synchronous child-process API rather than the async variants, acceptable because it's boot-only.
- **Recommendation:** Switch to async execFile (promisified) for netstat/taskkill so boot isn't blocked, and cap/stream the netstat output. Low priority since it's a rare recovery path, but trivial to fix.

#### ~~`PROXY-02` — res.json() serializes the entire 100-500MB sync result with a single synchronous JSON.stringify on the main thread~~  ❌ *dismissed on verification*

- **Severity:** ❌ INVALID _(finder rated critical; corrected on verification)_  ·  **Effort:** M  ·  **Confidence:** 0.9
- **Category:** blocking-cpu
- **Locations:** `server/src/index.ts:125`, `server/src/index.ts:141`, `server/src/index.ts:163`, `server/src/services/syncOrchestrator.ts:335-342`
- **Evidence:** The full-sync handler returns the complete converted dataset: index.ts:125 `if (!res.writableEnded) res.json(result);` where `result.masters.tallymessage` and `result.transactions.tallymessage` hold every converted master and voucher (syncOrchestrator.ts:339-340 `masters: mastersResult?.data`, `transactions: vouchersResult?.data`). Express's res.json() calls JSON.stringify(result) synchronously. The project brief states the parsed/converted objects total 100-500MB of JS. sync-masters (index.ts:141) and sync-daybook (index.ts:163) do the same. The frontend explicitly awaits this whole blob: tallyApi.ts:47 `const j = await r.json();`.
- **Impact:** JSON.stringify of hundreds of MB is a multi-second (potentially 5-15s) fully-synchronous main-thread freeze that happens AT THE END of an already-long sync — the worst possible moment, when the user expects completion. It also transiently doubles memory (the source object tree plus the serialized string buffer), risking pressure against the renderer's 2GB cap and the main process. This stall is in addition to PROXY-01's parse stall.
- **Root cause:** The proxy returns the full materialized dataset in one HTTP response body instead of streaming it, and Express's res.json has no async/streaming variant. Combined with in-process hosting (electron.js:134), the stringify blocks the UI loop.
- **Recommendation:** Stream the result instead of buffering+stringifying: write NDJSON (one voucher/master per line) via res.write() in batches with setImmediate yields, or move to utilityProcess (PROXY-01) so the stringify happens off the UI thread. Better still, since both client and server live in the same Electron app, persist the converted data to IndexedDB/Supabase server-side and have the renderer read it back incrementally rather than shipping 100-500MB through an HTTP round-trip the app makes to itself.
- **🔍 Verification:** The structural claims are accurate but the impact is wildly overstated. CONFIRMED code facts: index.ts:125/141/163 call res.json(result) synchronously; syncOrchestrator.ts:339-340 packs the full masters/vouchers tallymessage arrays into the response; tallyApi.ts:47 awaits r.json(); and electron.js:134 hosts Express in the Electron MAIN process via require(serverDist), so the stringify runs on the main-process event loop (NOT the renderer's 2GB-capped V8 as the finding's memory-pressure argument implies).\n\nThe core defect in the finding is conflating two different numbers. The brief's '100-500MB of JS objects' describes the in-RENDERER parsed working set (Maps of items/ledgers + derived indices + prediction-engine intermediates). The HTTP response payload is something else entirely: the converted canonical objects (convert.ts:360-375) are LEAN — a voucher is a handful of short strings plus small allledgerentries/allinventoryentries arrays, with no retained raw XML. I measured a representative payload: a realistic full-year sync (~4,800 vouchers per MEMORY.md validation + ~1,063 masters) serializes to ~15MB and JSON.stringify takes ~31ms on the main process. Stress-testing upward: 20k vouchers=8MB/18ms, 50k=20MB/47ms, 100k vouchers (decades of this business's volume)=40MB/89ms. V8's JSON.stringify is native C++ and does not enter the multi-second range until hundreds of MB of actual serialized OUTPUT — a size this data shape cannot reach. The claimed '5-15s fully-synchronous freeze' is off by roughly two orders of magnitude.\n\nAdditionally: this path runs at most every 30 min (auto-sync) or on a manual sync button — not a hot path — and the ~31ms stringify is amortized into a multi-minute sync operation. The transient memory doubling (object tree + string buffer) is ~15-40MB, trivial against the main process budget and irrelevant to the renderer cap since it happens in main. The minor real smell — shipping the full materialized blob over an HTTP round-trip the app makes to itself — is a code-cleanliness/architecture point, not a critical blocking-CPU performance issue.
- **How to measure:** Instrument the actual stringify rather than trusting the 100-500MB figure. In server/src/index.ts wrap line 125 as: const t0=process.hrtime.bigint(); const body=JSON.stringify(result); const t1=process.hrtime.bigint(); console.log('payloadMB',(body.length/1048576).toFixed(1),'stringifyMs',(Number(t1-t0)/1e6).toFixed(0)); res.type('application/json').send(body); Run a real full-FY sync and read the two numbers. Confirm payload is ~10-20MB and stringify is well under 100ms. To double-check the renderer side, in tallyApi.ts:47 time the await r.json() the same way. Only if you observe payload >150MB or stringify/parse >500ms in a real sync does this rise to even a medium concern. A quick offline check: JSON.stringify(result).length right after an orchestrator.syncAll() in a node REPL against a captured full-year result object.
- **Refined recommendation:** Do not treat this as a critical CPU-blocking fix. At measured scale (~15MB / ~31ms) no action is warranted. If you still want to eliminate the redundant self-HTTP round-trip on principle (real but low priority), the right move is the finding's last suggestion: since client and server share the Electron process, have the orchestrator persist converted masters/vouchers to IndexedDB/Supabase server-side and signal the renderer to read incrementally, rather than shipping the blob through a localhost HTTP call. NDJSON streaming with setImmediate yields would only matter if the payload ever grew past ~150MB of serialized output, which this lean canonical shape will not reach for this business. Skip the utilityProcess move for THIS reason (the stringify is already off the renderer thread and is sub-100ms); evaluate utilityProcess only against PROXY-01's parse cost on its own merits.
